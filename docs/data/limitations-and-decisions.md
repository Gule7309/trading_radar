# 已知限制、設計決策與名詞

使用資料或向他人說明系統時，請先看這份。每一條都標明「影響」與「怎麼處理」。

## 已知限制

| # | 限制 | 影響 | 怎麼處理 |
|---|---|---|---|
| 1 | **產業分類粒度不一致**：約 185 檔現行股票只有上層分類「電子工業」，其他是細分產業（如「半導體業」） | 「電子工業」組比其他組大，該組 percentile 的比較基礎較雜 | 已在輸出標示 `percentileScope`；此版不修正 |
| 2 | **財報可用日是估計值**（Q1 5/31、Q2 8/31、Q3 11/30、Q4 次年 3/31），不是實際公告日 | 回測偏保守（晚於實際公告），不會有前視偏誤 | 輸出欄位名為 `availabilityCutoff`；UI 顯示「可用日期（估計）」 |
| 3 | **月營收與行情沒有逐列抓取時間** | Evidence 只能提供資料集最近更新時間 | `fetchedAtScope = "dataset"` 誠實標示；財報為 `row` |
| 4 | **`delisted_stocks` 含「上櫃轉上市」**（約 89 檔仍在交易） | 若用它判斷已下市，會誤刪正常股票 | 一律用 `stocks.is_active`；Screening 不使用此表 |
| 5 | **金融業不適用排名模型**（銀行、金控、保險、證券、其他，約 40 檔） | 這些股票不會出現在 Candidate | 資料仍保留可查；之後需要時另建模型 |
| 6 | **部分股票的營收 YoY 與來源值不一致**（2026-08 約 6 檔，多為營收重編或基期不同） | 這些股票不進排名 | 狀態保留在 `screening_results` 供稽核 |
| 7 | **`stock_universe_history` 只有 2026-07-31 一份** | 不能直接重建「歷史上某天有哪些股票」 | `stocks` 保留 406 檔已下市代號、歷史行情也保留，可降低存活者偏差；嚴謹回測需另建 |
| 8 | **價格未做除權息還原** | 長期報酬會被除權息跳空扭曲 | 搭配 `dividend_events` 自行還原 |
| 9 | **Release 快照是靜態的** | 隊友的資料可能落後維護者 | 依 [operations.md](operations.md) 定期發佈；JSON 的 `run` 會寫明資料時點 |
| 10 | **`sourceSnapshot` 只在 manifest 與資料版本一致時才有值** | 每日更新後新 run 的 `sourceSnapshot` 會是 `null` | 發佈前執行 `taiwan-data manifest`；`dataVersion` 永遠有值 |
| 11 | **`sourceUrl` 多為 API 端點** | 瀏覽器直接開不一定是好讀的頁面 | `referenceUrl` 預留給人看的頁面，目前為 `null` |
| 12 | **預設結果偏向高成長股** | 營收年增數百 % 的股票容易排在前面 | 這是三因子等權的結果；可用 `weights` 調整，或由 Agent 層解讀 |

## 設計決策與理由

| 決策 | 理由 | 放棄的替代方案 |
|---|---|---|
| **單一 SQLite 檔** | 讀多寫少、每日一次批次寫入、三人團隊與本機 Demo；不需要伺服器、可離線 | PostgreSQL／雲端 DB：搬遷成本高、需維運，此階段沒有多人同時線上查詢的需求 |
| **雲端存快照，每人本機一份** | 避免多人共用同一個 SQLite 造成 lock、WAL 與同步衝突；Demo 不依賴網路 | 共用雲端硬碟中的檔案、直接讀寫遠端資料庫 |
| **GitHub Release 分發** | 不需另開雲端帳號；單檔上限 2 GB 足夠；資料本來就是公開資料 | GCS（之後上雲時再考慮） |
| **Percentile 先算，使用者條件後套用** | percentile 代表公司在產業中的相對位置，不應因使用者條件而改變 | 先篩選再算 percentile（同一家公司在不同使用者看到的 percentile 會不同） |
| **三因子等權，流動性只當門檻** | 指標少而清楚，容易解釋；流動性代表「能不能交易」，不代表「好不好」 | 加入法人、融資、技術指標等更多因子 |
| **預設最低流動性 1 億元／日** | 排除很難交易的小型股，又不會過度偏向大型股；沒有門檻時第一名日均成交僅 0.9 億元 | 不設門檻 |
| **只發布 verified 的數字** | Agent 引用的每個數字都必須能被重算與交叉驗證 | 允許部分驗證的數字出現，讓使用端自行判斷 |
| **營業利益率用單季值** | 累計值在不同季度不能比較 | 年初至今累計值 |
| **所有股票共用同一營收月份與財報季度** | 避免「A 公司用 9 月、B 公司用 8 月」卻放在一起排名 | 各用各自最新資料 |
| **Coverage gate 95%，可設定** | 營收在每月 10 日前陸續公布，涵蓋率不足時不能拿來做全市場比較 | 只要有資料就用 |
| **缺資料不補值** | 補值會讓數字看起來可信但其實沒有來源 | 以 0、平均值或來源值補 |
| **Evidence 存值不存參照** | 資料庫更新後，舊的分析仍可原樣重現與稽核 | 每次讀取時重新查原始表 |

## 名詞

| 名詞 | 意義 |
|---|---|
| **Candidate** | 通過所有檢查並有名次的候選股票 |
| **Evidence** | 一個數字的出處：來源、期間、公式、原始輸入與驗證狀態；以 `ev-001` 這類 ID 引用 |
| **Screening run** | 一次篩選的完整結果，以 `runId` 識別，可原樣重現 |
| **Universe** | 所有股票（含已下市），是對帳的起點 |
| **Base exclusion** | 與使用者無關的排除：已下市、非一般業、缺資料、驗證未通過、財報不是共同季度 |
| **Hard constraint** | 使用者設定的排除條件：產業、負債比上限、最低流動性、處置股 |
| **Percentile** | 0–1 的相對位置，越高越好；同產業不足 5 檔時改用全市場 |
| **Coverage** | 某月份（或季度）有資料的公司數 ÷ 前一期的公司數 |
| **Coverage gate** | 涵蓋率未達門檻就退回上一個完整期間 |
| **Availability cutoff** | 估計可以合理取得該財報的日期，用來避免前視偏誤 |
| **Point-in-time / 前視偏誤** | 回測時只能用「當時已經公布」的資料；用到未來才公布的資料就是前視偏誤 |
| **`data_version`** | 由各資料集最近更新狀態算出的版本摘要，用來判斷資料是否變過 |
| **Manifest** | 記錄檔案大小、SHA-256 與筆數的 JSON，用來驗證資料沒有損毀或被換掉 |
| **WAL** | SQLite 的寫入日誌檔（`-wal`）；未合併前裡面有資料，不能刪 |
| **一致性備份** | 用 `VACUUM INTO` 產生的備份，保證是某個時間點的完整狀態 |
